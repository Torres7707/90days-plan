# 如何审核 AI 写的代码（马克的技术工作坊）

视频：https://www.youtube.com/watch?v=h0ALH6qBb7k
原文：Anthropic《How the Claude Code team does code review》 https://claude.dev/blog/solving-code-review-at-anthropic/
整理日期：2026-11-01（根据视频字幕整理，下面是视频作者对原文的转述和他自己的看法；我没有逐句对照原文）

## 背景

- Claude Code 自己约 90% 的代码是 AI 写的，那怎么保证质量？
- 两个极端都不行：逐行看（AI 几分钟写几千行，看不过来）；只审"重要部分"（问题常出在看起来不起眼的地方）。
- 代码审核不是孤立环节，和整个发布流程连在一起，所以文章讲的是**整条流程**。

## 四个阶段

| 阶段 | 做什么 |
| --- | --- |
| PR 前 | 确保产品能跑；检查代码质量 |
| PR 中 | CI → AI 审核 → 安全审核 → 按风险审批 |
| 合并时 | 合并队列 |
| 合并后 | 功能开关、逐步上线、观察和回滚 |

## PR 前

1. **确保产品能正常运行**：给 AI 工具（运行程序、看网页、截图、操作电脑），让它写完能自己验证。重点是让 AI 具备**验证产品效果**的能力。
2. **检查代码质量**：用一个**全新的 agent**，只给它"目标 + 代码改动"。
   - 写代码的 agent 回头检查，会顺着原来的思路走，容易以为自己写对了。
   - 新 agent 没有之前的思考过程，看起来是缺陷，反而更客观。

## PR 中

**CI**：Lint、类型检查、多平台测试、构建等，不需要 AI、能自动跑的检查都放这里。

**AI 审核**（三步）：
1. **发现问题**：从三方面查：有没有达到目标、和现有系统合不合得来、会不会影响别的地方。
2. **筛选问题**：把无关紧要的（代码风格、冗余代码等）过滤掉。大多数开发者都觉得无所谓的，写成筛选规则交给负责筛选的 AI。
3. **处理问题**：留下的分三类：重要问题、小问题、已有问题（不是这次改动带来的）。每一条都必须回应，要么改掉，要么写明理由关掉。有没处理的，PR 就不能往下走。

**AI 审核的三个优化方向：**

1. **找出真正的问题：用线上事故做评测集**
   - 每次线上出问题，记两样东西：出了什么问题、哪个 PR 引入的，合起来就是一个案例，多个案例组成评测集。
   - 做法：把案例里的 PR 拿给 AI 审核，看它有没有找到真实问题，找到得 1 分，没找到得 0 分，总分是"基准分"。
   - 改提示词、换工具、换模型后，用同一个评测集再打分，分数涨了才保留修改。
2. **少提没用的意见**
   - 上面的评测只看"找没找到"，报得越多越容易得分，但没用的意见也越多，浪费开发者时间。
   - 两种方法识别无效意见：
     - 看 PR 作者怎么处理每条意见：改了（有用）/ 说它错了 / 说是故意这样写 / 觉得无所谓（后三类都算无效）。
     - 拿确认没有问题的 PR 去审，提出的意见基本都是无效的。
   - 之后每次调整，既要看评测分数有没有涨，还要看无效意见有没有变少。
3. **审核要能正常结束**
   - 问题：AI 审核提意见 → 写代码的 AI 改 → 再审 → 又提新意见，没完没了。文章里有个 PR 一晚上来回改了 50 多轮。
   - 四条规则：
     1. 超过三轮还没通过，提醒作者停下来想想是不是整体思路有问题。
     2. 前几轮看整个 PR 和它影响到的地方；之后只看新改动的那几行。（每轮从头看，总能翻出之前就存在的新问题，永远停不下来。）
     3. 同类问题一次全部指出，不要每轮挑一处。
     4. 已经提过的意见不要重复提。
   - 效果（按视频转述的原文数据）：一轮就通过的 PR 比例从 65% 涨到 78%。

**安全审核**：单独的一轮自动审核，专查安全问题，没处理完 PR 就不能合并。（原文写得不多）

**按风险审批：**
- 低风险（文档、文案、仅内部员工用的功能）：自动检查通过就行，不用人批准。
- 中风险（普通产品改动、缓存、自动更新等敏感处）：1 人批准。
- 高风险：2 人批准。

## 合并时：合并队列

PR 不直接合进主分支，先排队。轮到它时，系统把它和**最新**的主分支合在一起再跑一遍测试，通过才真正合入。能拦住"单独测没问题，和别人的改动合在一起才出错"的情况。

## 合并后

1. **功能开关**：新功能先藏在开关后面，只对内部员工打开（他们每天大量使用，很多问题先在内部暴露），稳定后再对所有用户打开。
2. **逐步上线**：先发 latest（尝鲜版），大约一周没大问题再推到 stable（稳定版）。
3. **观察和回滚**：最快是远程关开关；开关解决不了就重新构建发布。

## 一个 bug 要闯多少关

AI 跑测试 → 新 agent 审代码 → CI → AI 审核 → 安全审核 → 按风险审批 → 合并队列 → 内部员工先用 → latest → stable → 观察/回滚。**没有哪一关完美，但层层串起来，bug 很难一路漏到用户手里。**

## 人最该做的五件事

1. 判断哪些事该做（方向、品味、功能范围）。
2. 审核高风险代码（计费、自动更新、CI 配置）。
3. 把关架构设计（它会被人和 AI 照着抄，错了会蔓延）。
4. 阅读证据，而不是每一行代码：测试输出、运行的命令、返回结果、截图、AI 的发现。
5. 为结果负责：AI 不能背锅。

## 结果和结论

- 数据（按视频转述）：6 到 9 月合并的 PR 翻了一倍多，需要回滚的比例反而下降 40% 以上。
- 核心：重新划分人和 AI 的分工。AI 做大量执行，人只做最关键的决策。和上一个视频的 **Humans steer, Agents execute** 一致。
- 作者观点：审核 AI 代码的本质，是怎么把人有限的注意力用在最关键的地方。

## 和我的 React 代码审查智能体的关系

（以下是整理者的对照，用来帮你想，不是视频里的内容）

| 视频里的做法 | 对应到我的项目 |
| --- | --- |
| 用全新 agent，只给"目标 + 改动" | 审查时不要把整段对话历史都发给模型（我的代码目前每次发整个历史，这一点已在记录的待改项里） |
| 发现 → 筛选 → 处理三步 | 可以把审查结果分成：重要问题 / 小问题 / 已有问题，让输出结构化（Zod） |
| 用真实事故做评测集 | 从公开仓库的真实 bug 修复 PR 里收集案例做评测集（计划里已定"只用公开来源，不用公司代码"） |
| 少提没用的意见 | 评测时不仅看"找到没"，还要统计误报 |
