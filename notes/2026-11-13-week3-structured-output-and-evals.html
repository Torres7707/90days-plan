1. 本周真正目标

第 3 周要做的，是把「一大段文字评审」变成一张张结构化问题卡片，再用一组固定用例去衡量提示词好不好。指南里的四步是连在一起的：

  1. 第 2 步：流式渲染结构化结果。本练习走的是路径 A：streamText + Output.object({ schema }) + partialOutputStream。渲染发生在终端里的文本格式化，不是真正的网页 UI，也没有用 useObject。
  2. 第 3 步：准备 24 条用例，12 条 find（应报出问题）、12 条 clean（不应乱报），写在 evals/cases.json。
  3. 第 4 步：批量脚本对每条用例调用 generateText 跑 3 次，再汇总。当前自动统计的是「有没有报问题」，不是「报得对不对」。
  4. 第 5 步：用 MockLanguageModelV4 和 simulateReadableStream 做不花钱的离线测试。这一步还没写完。

框架先放在这里：schema 校验成功，只保证对象长得像评审结果。它不能保证模型找对了 bug，也不能保证 clean 用例真的无问题。自动脚本能稳健完成的，是「报没报」；「报没报对」要靠人工对照原文。如果把前者叫做召回率，后续改提示词时就会改错方向。

3. 全局数据流

4. 第 2 步：流式卡片（终端，路径 A）

流式结构化输出的核心机制是：对象不是等全部生成完才出现，而是一帧帧变长。某一帧里，issues 可能还是 undefined，某一张卡可能只有 title，severity 仍是 undefined。所以渲染必须容错：缺字段时用占位，不能把 "undefined" 印出来；卡片编号用数组下标，不能用可能还没生成完的 title 当编号。

当前已经实现的

src/render-partial.ts 用 ?? "生成中..." 给缺字段占位，并用 问题#${i + 1} 编号。它还接收第二个参数 isFinal（默认 false）：流式过程中空数组显示「卡片生成中...」；若调用方声明这是最终结果且 issues 为空，则显示「没有问题」。

export function renderPartialReview(partial: PartialReview, isFinal: boolean = false): string {
  const {issues} = partial;
  if (!issues||issues.length === 0 && !isFinal) {
    return `卡片生成中...`;
  } else if (issues.length === 0 && isFinal) {
    return `没有问题`;
  }
  // ... title??"生成中..." 等
}

src/step2-stream.ts 在 for await (const partial of result.partialOutputStream) 里按帧渲染（此时不传 isFinal，默认还在生成）。循环正常结束后，再 const finalReview = await result.output，并调用 renderPartialReview(finalReview, true)。这正是关键分工：render 函数自己不知道流结束了没有，结束态要由调用方提供。

建议，尚未完全做到的

不要把下面写成「已经修完」。这是对照当前实现后的说明。

  • renderPartialReview 里判断写成了 !issues||issues.length === 0 && !isFinal。&& 先于 || 运算，所以当 issues 还是 undefined 且 isFinal === true 时，会因为 !issues 为真而仍显示「卡片生成中...」，进不了「没有问题」分支。正常的最终 result.output 若通过 schema，issues 应是数组，常见终态不受影响；这是边角，不是「已经完美区分」。
  • src/step2-preview.ts 回放夹具时没有在全部帧结束后再用 isFinal: true 渲染一次。当前夹具最后一帧本身有问题卡片，所以预览看起来没问题；若最后一帧是空数组，仍会像还在生成。
  • 评测脚本已经对单次失败做了记录并继续往下跑。但 src/step2-stream.ts 循环外的 await result.output 仍未包 try/catch：若最终对象校验失败，流式脚本还是会中断。无论哪条路径，失败都不能当成 issues: [] 的 clean。

文件头里还有「写完 TODO 之前不会调用模型」的旧说明，和现在已经接上 streamText 的事实不一致，以代码为准。

6. 第 4 步：批量评测怎么跑

把 scripts/eval.ts 想成一条管道，而不是一堆命令。每一段都有自己的职责。

环节做什么
process.argv.slice(2)只看传给脚本的参数，不包含 node / tsx / 文件名。例如 pnpm eval 时这里通常是空数组。
parseArgs有没有出现独立参数 --run；若有独立参数 --limit，再读它后面那一个参数当条数。
loadCases读 evals/cases.json，先 JSON.parse 再交给 Zod 的 evalCasesSchema。形状不对会在进模型前失败。
selectedlimit 为空则用全部用例，否则 cases.slice(0, limit)，只取从开头数的前 n 条。
run === false打印已加载条数后直接 return。不调用 reviewOnce，不写结果文件。这是默认的安全档。
reviewOnce对单条用例调用一次 generateText，output: Output.object({ schema: reviewSchema })，提示词只有代码。返回值是联合类型：成功带上 review，失败带上 error。
result.output取完整结构化结果。当前用 try/catch 接住校验失败或抛错；output 为空也记为失败，然后继续跑后面的次数和用例。
判定与汇总只把成功次数交给 hasReportedIssue 和统计；失败另栏列出，「未计入报出率」，也不会当成 clean。最后把 promptVersion、date 和全部 attempts（含失败）写成 results/results-*.json。

为什么默认是 --run === false

parseArgs 用的是 argv.includes("--run")。只有参数列表里真的出现这个标记，才会进入评测循环。package.json 里 pnpm eval 只执行 tsx scripts/eval.ts，没有带 --run，所以 run 为 false，不会打模型。真正评测要用 pnpm eval:run，它已经在脚本里写上了 --run。

--limit 怎么写才有效

当前 parseArgs 只认空格分开的 --limit 1，也就是 --limit 后面跟一个单独的 1。它不支持 --limit=1：代码用 indexOf("--limit") 找的是完整参数，找不到就把 limit 当成「未设置」，结果会跑全部 24 条。文件头注释里若仍写着 pnpm eval:run -- --limit=1，那是过时写法，以代码为准。

一条安全、且和当前 parseArgs 一致的命令：

pnpm eval:run -- --limit 1

中间的 -- 是把后面的参数交给脚本，而不是交给 pnpm。这只会选中第 1 条用例，再重复 3 次，共 3 次模型调用。先这样确认通了，再考虑去掉 --limit 做全量。

7. 评测循环与统计流程

8. 从关键词判对到「只看有没有报」

最初的辅助判定是：find 用例要把一条 review 里所有卡片的 title / reason / suggestion 拼成一段文字，再要求 keywords.every(keyword => text.includes(keyword))。这会带来几层问题，不能靠改成 some 来掩盖：

  • 模型完全可能用自己的话说明了正确的问题，但一个规定关键词都没出现。今天实际遇到的就是这类情况，于是全部 find 都被判失败。
  • 反过来，短词（如 id、for、hook）很容易在无关描述里出现。跨多张卡片拼接后再 includes，还可能一张卡贡献一半词、另一张卡贡献另一半词，整组 every 仍然通过。那不是「报对了」，只是字面上凑齐了。
  • 合法 JSON 只说明形状对。关键字命中仍然只是粗筛。三次都「命中」只说明这个粗筛稳定，不证明内容正确。

晚上协商后，辅助逻辑改成了现在的 hasReportedIssue：只看 issues.length > 0。find 上这叫「报出了问题」，clean 上这叫「报了问题（程序把它计为误报候选）」。两边都不再把这个布尔值叫做正确命中。关键词仍留在用例里，打印时作为「仅供人工对照」的预期，不参与自动判定，也没有进入 buildReviewPrompt。

export function hasReportedIssue(review: Review): boolean {
  return review.issues.length > 0;
}

自动数字因此改叫 find 用例报出率 和 clean 用例误报率。前者不是正确识别召回率。人工栏一律是「待核对」，脚本不会因为报出了就把这条标成正确。

9. 统计口径：用例级、运行级，以及旧错误

当前 summarizeReportStats 把 find 和 clean 分开，并且同时给出两套分母不同的比率。不要把它们混成一个数。

旧实现（已改正）当前实现
分母 find 和 clean、3 次重复，全部倒进同一个 results.length 用例级分母是该类用例数；运行级分母是该类成功记下的运行次数
分子 把所有 isHit === true 算「发现了」，把所有 false 算「误报」。于是 clean 上「正确不报」被算进发现，find 上的漏报被算进误报 find 只统计「报出了问题」的 find；clean 只统计「报了问题」的 clean
3 次如何进分子 一次运行被当成一条用例，样本量被扩大了 3 倍 用例级：同一条的 3 次先汇总，至少 1 次报出才计入该用例；运行级：每次运行单独计数
看起来像什么 两个率永远加起来是 100%，完全分不清召回和误报 两个率不再互补；但 find 报出率仍然不是正确召回率

用文字写公式（当前代码，分母为 0 时比率为 0）：

用例级 find 报出率 ＝（至少有一次报出问题的 find 用例数）÷（find 用例数）

用例级 clean 误报率 ＝（至少有一次报出问题的 clean 用例数）÷（clean 用例数）

运行级 find 报出率 ＝（报出问题的 find 运行次数）÷（find 运行次数）

运行级 clean 误报率 ＝（报出问题的 clean 运行次数）÷（clean 运行次数）

这里的「运行次数」都是成功得到完整 Review 的次数。失败次数另计，不进这两个分母，也不进分子。因此失败不会被算成 clean，但也不会把「三次全失败」的用例算进用例级分母。

「至少 1 次」不表示稳定。一条 find 用例 3 次里只有 1 次报出，用例级仍计入分子，但运行级会暴露 1/3。三次重复的意义是观察波动：模型这次报、下次不报，说明不要只跑一次就下结论。三次都报出，也只说明「报没报」这件事稳定，不说明每次都报对了。

10. 贯穿教学示例与四象限

以下是教学示例，用来讲清机制。它不是某次真实模型输出，也没有编造评测分数。

假设有一条 find 用例：组件在 if (!id) return null 之后才调用 Hook。预期是人能看出「条件调用 Hook」。程序不会用关键词去判对，只看有没有 issue。

次数模型输出（示例）程序看到的人工应想的
第 1 次 报了「提前返回之后才调用 Hook」，措辞里未必有设定关键词 报出问题 待核对。看起来像报对了，但程序并不知道
第 2 次 只报了「变量名不够好」 仍然是报出问题 待核对。可能报错了对象，不能因为「有 issue」就算召回
第 3 次 issues: [] 未报问题 这一次漏报了。三次并不稳定

按当前口径：这条 find 用例在用例级会计入「报出」（因为至少 1 次报了）；运行级是 2/3。如果你只看用例级，会以为「这条已经覆盖」，但波动还在，而且 2 次报出里可能只有 1 次是报对的。

clean / find 与报出 / 报对

程序：报出了问题程序：未报问题
find（希望抓住真问题） 计入报出。是不是报对了，仍待核对 可以看作自动可见的漏报（没报出来）
clean（希望不要乱报） 程序把这计为误报候选；若用例其实暗藏问题，人工可能不同意 程序看到没报。若用例本身真干净，这才接近「不误报」

所以「报出」和「报对」不是同一根轴。程序现在只负责左列/右列里「有没有报」；上下两行的语义对错，取决于用例写得是否可信，以及你是否对照了原文。

人工检查的前提是：你自己相信这条用例的预期。如果一条被标成 clean 的代码其实有 hook 问题，那么模型报出来反而是对的，程序却会把它算进误报率。评测不能保证每一次 review 都正确，也不能保证尺子本身完美。以后可以改进判定或补人工标记，但不需要在当周再搭一套自动裁判或对照答案生成器。

命令调用真实模型？大约几次

13. 今天容易混在一起的点

今天前半段如果先陷进某一行代码，会很难建立全貌。更清楚的顺序是：先认数据从哪来、到哪去，再看某一帧或某一次判定。

  • 合法输出 ≠ 内容正确。schema 能 parse，只说明形状对。
  • 报出 ≠ 报对。hasReportedIssue 只回答有没有 issue。
  • find 报出率 ≠ 召回率。召回要回答的是「该找出的问题里真正找出了多少」，自动脚本现在做不到这一步。
  • 至少 1 次报出 ≠ 稳定，三次稳定 ≠ 正确。
  • 用例级分母和运行级分母不能混用。旧实现把所有次数倒在一起，两个率加起来永远是 100%，那是计数错误，不是什么深刻结论。
  • keywords 是给人看的预期，不是给模型的提示，也不是现在的自动判分依据。不能为了让关键词对得上就去改用例或提示词。
  • 空数组在流中间和流结束含义不同。render 不知道结束了没有，要由 for await 未结束 / 正常结束后的 isFinal 来告诉它。评测里的失败已被单独记录；流式脚本的最终 output 若抛错仍会中断。无论哪种，都不能用空 issues 去冒充 clean。
  • 本练习的「卡片」是终端文本，不是网页组件。路径 A 已经足够完成本周这条线。
  • 命令不要写成 --limit=1。当前解析器不认它，会变成全量 72 次调用。正确是 pnpm eval:run -- --limit 1。
